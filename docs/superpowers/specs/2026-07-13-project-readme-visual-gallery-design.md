# D3D11 Project README Visual Gallery Design

## Goal

Polish the 37 tutorial project READMEs so a reader can understand each sample at a glance and immediately move between projects. Every project receives a consistent top information image, a newly captured runtime screenshot, a short runtime GIF, and previous/main/up/next navigation.

The visual direction is the approved **B layout: runtime screen plus summary**. The real application screen is the primary visual; the project number, title, one-sentence purpose, and technology tags provide compact context beside it.

## Scope

- Cover the 37 projects listed in `tools/readme_media_manifest.json` in manifest order.
- Keep the duplicate `Dx11/16_pmxWithMotion` directory outside this 37-project sequence, matching the existing capture and root README scope.
- Update each selected project's `README.md` without deleting its existing technical explanation.
- Refresh the root README's media references or captions only where required by the new captures.
- Do not change tutorial rendering behavior solely for documentation unless a deterministic capture hook is required to expose an existing feature.

## Considered Approaches

### A. Explanation-first poster

Place a large title and concept summary above a smaller runtime image. This resembles a traditional tutorial diagram, but it delays the actual visual result and duplicates the prose already in the README.

### B. Runtime screen plus summary (selected)

Use a real runtime screenshot on the left and a compact summary panel on the right. This makes the application result immediately recognizable while retaining enough instructional context for scanning 37 projects.

### C. Full-screen image with text overlay

Overlay the title and description directly on the runtime capture. This is visually compact, but readability varies with bright scenes and debug windows, and it obscures details the reader may want to inspect.

## Manifest As Single Source Of Truth

Extend `tools/readme_media_manifest.json` so each project entry owns:

- sequence number and project directory;
- executable and launch/capture environment;
- title, one-sentence summary, and three to five technology tags;
- load wait and deterministic interaction sequence;
- screenshot, GIF, and information-image output paths.

Capture, poster generation, README updates, and validation all consume this data. This prevents numbering, filenames, descriptions, and previous/next links from drifting apart.

## Capture Workflow

1. Build or confirm the Debug x64 executables used by the manifest.
2. Launch one project at a time with its documented capture environment.
3. Wait for project-specific resource loading, then perform the manifest's interaction sequence.
4. Capture a clean 1600x900 client-area PNG.
5. Record four to five seconds of real runtime activity and encode an 800x450, 8 fps, palette-optimized GIF.
6. Close the process cleanly and write the result to the capture report.

Animated samples show their principal animation or transition. Static samples use a short camera movement or an existing feature toggle so their GIFs demonstrate a real runtime change rather than repeating one frame. Project-specific clicks or key holds are declarative manifest actions, not hard-coded capture-script branches.

Each GIF targets at most 5 MiB. If a scene cannot remain legible under that limit, reduce duration before reducing its 800x450 display resolution. The full-resolution PNG remains available for detailed inspection.

## Information Image Generation

Generate each 1600x640 information PNG from the freshly captured screenshot and manifest metadata:

- left region: uncropped or minimally cropped real runtime image, preserving the lesson's visible subject;
- right region: project number, exact project title, one-sentence purpose, and technology tags;
- restrained graphite interface with neutral accents so it does not compete with scene colors;
- consistent spacing, zero negative letter spacing, and text wrapping that prevents clipping;
- Korean-capable system font with a defined fallback.

The image is generated by a repository tool rather than hand-edited. Re-running the workflow therefore produces consistent posters after future screenshot or wording changes.

## README Template

Every project README uses this order:

1. centered top navigation;
2. B-layout information PNG;
3. existing project heading and technical explanation;
4. fresh runtime screenshot and GIF, labeled clearly;
5. repeated navigation at the bottom for long pages.

Navigation semantics are fixed:

- **Previous**: previous manifest project;
- **Main**: repository root `README.md`;
- **Up**: the parent `Dx11` directory;
- **Next**: next manifest project.

Project 01 renders Previous as non-linked text, and project 37 renders Next as non-linked text. All other links use relative repository paths so they work in GitHub and local Markdown viewers.

Existing technical sections, code notes, tables, and warnings are retained. Repeated legacy image blocks may be consolidated only when they show the same file without adding information.

## Failure Handling

A project capture fails if any of the following occurs:

- the executable does not start or does not expose a usable client window;
- the required model, scene, or character is absent after the load wait;
- the captured frame is blank, near-uniform, or materially smaller than the required dimensions;
- the GIF cannot be decoded or has no meaningful frame-to-frame change;
- an output path or README link falls outside the manifest contract.

The workflow records the failure, terminates the affected process, and retries that project once. A second failure remains visible in the aggregate report and makes the verification command fail; it is not silently accepted.

## Verification

Completion requires all of the following evidence:

- Debug x64 build succeeds for the tutorial solution or all manifest executables are freshly verified;
- all 37 processes launch and all 37 PNG/GIF/info-image triplets are produced;
- PNG and GIF decoders accept every output;
- image dimensions and GIF frame timing match the specification;
- blank-image, pixel-variance, and GIF motion checks pass;
- a 37-project PNG contact sheet is inspected for framing, loading, and readable subjects;
- representative frames from every GIF are inspected, with special attention to character and animation projects;
- every selected README contains valid top and bottom navigation plus the correct information PNG, screenshot, and GIF;
- root README media references remain valid;
- `tools/verify_readme_media.ps1` and `git diff --check` pass.

Character visibility is a release criterion: a technically valid image where the intended character is missing, tiny, clipped, or obscured is rejected and recaptured.
