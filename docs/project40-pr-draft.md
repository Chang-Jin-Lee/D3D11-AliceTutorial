# 40. MSAA와 Alpha-to-Coverage 비교

**PR 제목:** `feat: add MSAA alpha-to-coverage comparison lesson`

## 추가 이유

39번에서는 정렬 알파 블렌딩과 Weighted Blended OIT로 반투명 면의 합성 순서를 다뤘습니다. 40번은 같은 캐릭터의 레이스를 보며 삼각형의 기하 경계와 텍스처 알파 경계를 구분하고, MSAA만 적용한 결과와 Alpha-to-Coverage(A2C)를 적용한 결과를 비교합니다.

## 구현 내용

- Alpha Test 1x, Alpha Test 4x MSAA, A2C 4x MSAA 세 모드를 한 장면에서 전환합니다.
- 캐릭터 레이스 확대/전신과 고정 포즈를 제공하고, 대각선 기하 경계·알파 경사·가는 줄무늬·불투명 가림판이 있는 진단 장면을 함께 구성했습니다.
- HDR 색상과 깊이의 샘플 수를 맞추고, 4x 색상을 단일 샘플 HDR 텍스처로 Resolve한 뒤 노출·톤매핑·sRGB 변환을 한 번 적용합니다. 1x는 별도 Resolve 없이 색상 타깃을 직접 읽습니다.
- 4x 지원 여부, 현재 샘플 수, 장면/Resolve GPU 구간, 논리적 타깃 저장량을 HUD에 표시합니다. 지원되지 않는 4x를 1x로 바꾸어 4x라고 표시하지 않습니다.
- `1/2/3`, `C`, `O`, `S` 입력과 같은 기능의 ImGui 조작을 제공하고, 키 반복과 ImGui 키보드 입력 충돌을 막았습니다.
- 솔루션·앱 아이콘 대상·README 미디어 manifest에 40번을 연결하고, 기본 1x 실행 PNG/GIF와 같은 구도의 세 모드 비교 이미지를 추가했습니다.

구현은 [App](../Dx11/40_MSAA_AlphaToCoverage/App.cpp), [재질 분류와 정렬](../Dx11/40_MSAA_AlphaToCoverage/CoverageScene.cpp), [MSAA 파이프라인](../Dx11/40_MSAA_AlphaToCoverage/MsaaPipeline.cpp), [표면 셰이더](../Dx11/40_MSAA_AlphaToCoverage/40_Surface.hlsl)에 나누었습니다.

## 레이스 처리

원본 레이스는 glTF `MASK`입니다. 재질 인덱스 4, 전체 이름 `N00_002_01_Tops_01_CLOTH_02 (Instance)`, 원본 `MASK`가 모두 맞을 때만 비교 처리를 적용합니다. 조건이 어긋나면 다른 재질을 대신 선택하지 않고 원본 렌더링과 비활성 이유를 유지합니다.

Alpha Test는 텍스처·baseColorFactor·정점 알파와 비교 배율을 반영한 값에 cutoff를 적용합니다. A2C는 이 값을 cutoff로 이진화하지 않고 샘플 커버리지 입력으로 사용하므로 원본 MASK를 그대로 보존한 결과는 아닙니다. 알파 0은 두 처리에서 모두 버립니다. 눈처럼 원래 `BLEND`인 재질은 모든 모드에서 중심 깊이 기준 back-to-front, straight-alpha OVER, 깊이 쓰기 OFF를 유지하며 A2C 패스에 넣지 않습니다.

## 문제 상황과 확인 방법

- 4x MSAA만 켜면 삼각형 경계에는 여러 샘플의 커버리지가 생기지만, 픽셀 셰이더 `clip`으로 만든 레이스 안쪽 경계는 계속 이진적으로 잘릴 수 있습니다. 같은 포즈·카메라·배경·알파 1·cutoff 0.5·노출 1에서 세 모드를 각각 촬영해 비교했습니다.
- 고정 구도에서 Alpha Test 1x와 4x는 레이스 안쪽의 이진 모양이 비슷하게 남았습니다. A2C 4x는 중간 알파의 무늬를 더 남겨 이 구도에서는 레이스가 촘촘하고 덜 거칠게 보였습니다. 이를 모든 각도나 시간축에 대한 우위로 해석하지 않습니다.
- 진단 장면에서는 대각선 기하 경계와 텍스처 안쪽의 알파 경사·줄무늬를 나란히 확인했습니다. A2C 경사는 4개 샘플에 따른 유한한 단계로 보이며, 앞쪽 불투명 면의 깊이 가림도 유지됩니다.
- 대표 GIF는 기본 Alpha Test 1x 상태에서 약 4초 동안 카메라가 회전합니다. 앞·중간·끝 프레임에서 HUD는 1x를 유지하고 캐릭터 시점은 달라지는 것을 확인했습니다.

## 검증 결과

- Debug/Release x64 프로젝트 빌드와 시작 시 `40_Surface.hlsl` 엄격 컴파일을 확인했습니다.
- 재질·정렬·메모리 산식 31개 검사, WARP 픽셀 11개·GPU 타이밍 1개·제어 흐름 2개 검사, 39번 OIT 픽셀 8개와 장면 투명도 17개 회귀 검사를 통과했습니다. WARP 픽스처의 D3D11 InfoQueue에는 error/corruption과 warning이 없었습니다.
- README manifest, capture action, README updater/branding, 정보 이미지, 캡처 계약과 게시 미디어 검사를 각각 실행했습니다.
- 지원 장치에서 세 모드의 HUD 샘플 수가 1/4/4임을 확인했습니다. 게시 PNG는 1600×900, GIF는 800×450, 정보 이미지는 1600×640이며 캡처 후 앱 프로세스와 락이 남지 않았습니다.
- 리사이즈·최소화·복원, 모드/장면/구도 왕복, 반복 키 무시, ImGui가 키보드를 소유할 때 단축키 무시를 실행 화면에서 확인했습니다. 비교 알파·cutoff·노출 변경과 A2C cutoff 비활성도 별도 상호작용 세션에서 확인했습니다.

## 한계와 이후 계획

- A2C의 샘플 배치는 하드웨어에 따라 달라질 수 있으며 4개 샘플에서는 단계나 노이즈가 남습니다. 시간축 깜빡임을 완전히 제거하거나 모든 시점에서 더 낫다고 보장하지 않습니다.
- GPU 측정은 장면 렌더링과 4x Resolve 구간만 포함합니다. 최종 화면 변환, ImGui, swap-chain Present, CPU·드라이버 대기는 제외하며, 표시된 스냅샷 값으로 고정 성능 순위를 정하지 않습니다.
- 메모리 표시는 활성 색상·깊이·Resolve 타깃의 논리적 저장량입니다. 백버퍼, 모델, 텍스처, 드라이버 정렬·압축, 전환 중 임시 자원을 제외하므로 VRAM 사용량이 아닙니다.
- 사용한 장치가 4x를 지원해 미지원 장치 UI는 유도하지 않았습니다. 레이스 guard 불일치, 타깃 할당·셰이더·모델 초기화 실패, Present 실패, 장치 제거도 앱에서 fault injection하지 않았습니다. 리사이즈 실패의 장치 제거 판정은 제어된 HRESULT 검사와 호출부 검토로 확인했습니다.
- 앱 실행 세션의 D3D 디버그 로그는 수집하지 않았습니다. 위의 InfoQueue 결과는 WARP 픽스처에만 해당합니다.
- 비동기 타이밍의 최신 결과 선택, 건너뛴 타이밍 쿼리 요약, 변경된 cutoff와 원본 authored cutoff를 구분하는 HUD 문구는 후속 검토 항목으로 남깁니다.
